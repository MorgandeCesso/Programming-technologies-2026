## 2. Общие задания

### 2.1. Сервис и БД

На выбор ЯП и фреймворков ограничений нет. В примере к ЛР я использовал Python, FastAPI и PostgreSQL. 

Подключите локальную модель из предыдущей работы через библиотеку OpenAI и поддерживаемый сервером интерфейс. Параметры подключения и название модели вынесите в конфигурацию. Не включайте секретные ключи в репозиторий.

Архитектуру проекта, ORM и организацию модулей выберите самостоятельно. Сервис запускается локально, для демонстрации достаточно Swagger UI, Postman или другого HTTP-клиента. Отдельный фронтенд, авторизация и внешний деплой не требуются.

Создайте таблицы:

| Таблица | Обязательные данные |
|---|---|
| Справочник вашего варианта | Внутренний ID, уникальный код объекта, наименование; дополнительные характеристики по необходимости |
| Обработанные сообщения | Внутренний ID, время создания, исходный текст, категория, краткое содержание, извлечённый код и два дополнительных поля варианта, необязательная связь со справочником, результат сопоставления |

Заполните справочник не менее чем пятью учебными записями. Подготовьте воспроизводимый способ заполнения: скрипт, fixture или команду приложения. Код должен быть уникален с учётом выбранных правил нормализации. Не подменяйте внутренний ID записи кодом, извлечённым из текста.

### 2.2. Схема извлечения данных

Ответ модели должен содержать ровно шесть полей: общие `category` и `summary`, поле кода объекта и два дополнительных поля своего варианта, а также `details`. Поле `details` содержит дополнительные существенные сведения из сообщения, которые не вошли в остальные поля, либо `null`.

Все ключи обязательны. `category` и `summary` - непустые строки. Для полей кода, двух дополнительных полей и `details` разрешены строка или `null`. Отсутствующие сведения не придумываются. Для неоднозначной категории используется `other`.

Числа и даты на этом этапе извлекаются как текст: например, «около 30 экземпляров», «завтра вечером», «с 12 по 14 ноября». Пересчёт относительных дат и преобразование единиц измерения не требуются.

Составьте системную инструкцию с описанием полей, допустимых категорий и правил обработки отсутствующих сведений. Само сообщение передавайте отдельно. Небольшой перечень категорий задаётся в инструкции; полный справочник объектов модели не передаётся. Если пользователь указал только название объекта без кода, поле кода остаётся `null`, название можно сохранить в `summary` или `details`. Поиск по названиям и нечёткое сопоставление не требуются.

### 2.3. Проверитка результата

Разберите JSON и проверьте ответ по явно заданной схеме с помощью Pydantic, сериализаторов DRF или эквивалентного средства. Проверяйте наличие ключей, типы, допустимость категории, непустое содержание `summary` и отсутствие лишних полей. Пустые строки в nullable-полях либо приводите к `null` по описанному правилу, либо отклоняйте. Не преобразуйте произвольные списки и объекты в строки.

При невалидном JSON или нарушении схемы запись не сохраняется. Проверка схемы не доказывает фактическую точность извлечения: её нужно оценить сравнением с исходным текстом.

По извлечённому коду выполните поиск в БД. Допускается нормализация регистра и внешних пробелов при одинаковом применении к коду из сообщения и справочнику. Если объект найден, сохраните связь. Если не найден или код отсутствует, сохраните сообщение без связи, сохранив извлечённый код при его наличии. Различайте состояния `matched`, `not_found`, `not_provided`.

По ответу модели запрещено автоматически создавать или изменять записи справочника. Исходное сообщение и извлечённые сведения сохраняются. Модель не должна генерировать SQL и выбирать функции для исполнения.

Для обязательного объёма используйте сообщения об одном объекте и одном основном намерении. Обработку нескольких объектов можно добавить самостоятельно, но она не требуется.

### 2.4. Реализовать API

Вместо `{resource}` используйте ресурс своего варианта из таблицы раздела 1.

| Метод и путь | Назначение | Результат |
|---|---|---|
| `POST /{resource}` | Принять сообщение, вызвать LLM, проверить и сохранить результат | `201 Created`, созданная запись |
| `GET /{resource}` | Получить список сохранённых записей | `200 OK` |
| `GET /{resource}/{id}` | Получить одну запись | `200 OK` либо `404` |

Тело запроса создания имеет вид:

```json
{
  "message": "Текст сообщения по вашему варианту"
}
```

Ответ на создание и получение одной записи должен содержать ID, время создания, исходный текст, шесть извлечённых полей, ID связанного объекта либо `null` и состояние сопоставления. Эти служебные значения формирует приложение, а не модель. Структуру HTTP-ответа документируйте самостоятельно. При чтении записей повторный запрос к модели не выполняется.

| Ситуация | Поведение сервиса |
|---|---|
| `message` отсутствует, имеет неверный тип или содержит только пробелы | `400` или `422`, без вызова модели и сохранения |
| Запись с запрошенным ID отсутствует | `404` |
| Ответ модели не является валидным JSON или нарушает схему | `502`, без сохранения |
| Сервер модели недоступен | `503`, без сохранения |
| Превышен тайм-аут ожидания модели | `504`, без сохранения |
| Код объекта неизвестен или отсутствует | Успешное сохранение без связи со справочником |

Установите конечный тайм-аут. Ошибки возвращайте единообразно, с понятным типом или кодом и описанием, без секретов и внутренних трассировок. Повторные попытки необязательны; если они реализованы, их число должно быть ограничено.

## 3. Индивидуальные задания

### Вариант 0. Отзывы о товарах

Разработайте сервис, который извлекает сведения из отзывов покупателей. Справочник - товары с уникальным артикулом. Классифицируйте основную тему отзыва; оценку в звёздах определяйте только при явном указании пользователем.

- Категории: `quality` - качество товара; `packaging` - упаковка; `usability` - удобство использования; `other` - остальное или неоднозначная тема.
- Поле кода: `product_code` - артикул товара.
- Дополнительные поля: `rating_text` - явно указанная оценка; `usage_period` - срок использования.

Пример: «Пользуюсь чайником KT-204 две недели. Крышку чет неудобно открывать одной рукой. Ставлю 3 из 5».

```json
{
  "category": "usability",
  "summary": "Крышку чайника неудобно открывать одной рукой.",
  "product_code": "KT-204",
  "rating_text": "3 из 5",
  "usage_period": "две недели",
  "details": null
}
```

## 4. Проверка работы

Подготовьте собственные сообщения для своего варианта. Для основных сценариев выполните реальные запросы к модели. Для проверки ошибочных ответов и сетевых сбоев допускаются заглушки.

| № | Сценарий | Ожидаемое поведение |
|---|---|---|
| 1 | Полное сообщение с существующим кодом | Извлечение, классификация и связь с БД |
| 2 | Сообщение без кода и одного дополнительного сведения | Соответствующие поля `null`, сохранение без выдуманных данных |
| 3 | Сообщение с неизвестным кодом | Сохранение извлечённого кода и состояния `not_found`, справочник не меняется |
| 4 | Сообщение другой категории | Категория соответствует смыслу, а не одному шаблону |
| 5 | Сообщение, для которого подходит только `other` | Использование резервной категории |
