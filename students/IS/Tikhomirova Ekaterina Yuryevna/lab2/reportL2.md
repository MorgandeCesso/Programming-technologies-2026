# Лабораторная работа № 2

**Дисциплина:** Технологии программирования  
**Тема:** Разработка API для обработки предложений по учебным курсам с использованием локальной языковой модели  
**Выполнила:** Тихомирова Екатерина Юрьевна  
**Вариант:** 8

## 1. Цель работы

Разработать веб-сервис для обработки предложений студентов по учебным курсам. Реализовать извлечение структурированных данных с помощью локальной языковой модели, проверку результата, сопоставление кода курса со справочником и сохранение предложения в базе данных.

## 2. Постановка задачи

В соответствии с вариантом 8 сервис обрабатывает предложения об изменении содержания курсов, практических заданий и расписания.

Из исходного сообщения необходимо извлекать шесть полей:

- `category` - категория предложения;
- `summary` - краткое содержание;
- `course_code` - код курса;
- `topic` - тема предложения;
- `requested_change` - предлагаемое изменение;
- `details` - дополнительные существенные сведения.

Допустимые категории: `content`, `practice`, `schedule`, `other`. Все шесть ключей обязательны. Если сведения для заполнения поля отсутствуют, используется значение `null`, кроме обязательных непустых полей `category` и `summary`.

После проверки ответа модели приложение выполняет поиск курса по коду и сохраняет предложение. Если код отсутствует или не найден в справочнике, запись сохраняется без связи с курсом.

Сервис регистрирует предложения, но не изменяет расписание и учебный план автоматически.

## 3. Средства разработки и структура проекта

Сервис разработан на Python с использованием FastAPI. Для запуска приложения используется Uvicorn, для проверки данных Pydantic, для работы с базой SQLAlchemy и SQLite.

Локальная модель Qwen2.5-1.5B-Instruct запускается в LM Studio. Обращение к ней выполняется через библиотеку OpenAI. Настройки загружаются из переменных окружения с помощью python-dotenv.

| Файл | Назначение |
| --- | --- |
| `app/config.py` | Загрузка настроек приложения |
| `app/database.py` | Подключение к базе данных и создание сессий |
| `app/models.py` | Описание таблиц курсов и предложений |
| `app/schemas.py` | Проверка входного сообщения и результата извлечения |
| `app/llm.py` | Обращение к модели, разбор JSON и проверка ответа |
| `app/main.py` | Маршруты API, поиск курса, сохранение и обработка ошибок |
| `app/seed.py` | Начальное заполнение справочника курсов |
| `test_validation.py` | Автоматические проверки валидации и обработки ошибок |

В файл `.env` вынесены следующие параметры:

- `LLM_BASE_URL` - адрес сервера модели;
- `LLM_MODEL` - название модели;
- `LLM_API_KEY` - ключ доступа;
- `LLM_TIMEOUT` - время ожидания ответа;
- `DATABASE_URL` - строка подключения к базе данных.

Файл `.env`, виртуальное окружение, кеш Python и локальные файлы базы данных исключены из репозитория.

## 4. База данных

### 4.1. Справочник курсов

Таблица `courses` содержит внутренний идентификатор, уникальный код, название и описание курса. Внутренний идентификатор хранится отдельно от кода курса.

Справочник заполняется командой:

```powershell
.\venv\Scripts\python.exe -m app.seed
```

Перед добавлением проверяется наличие курса по коду. Повторный запуск заполнения не создает дубликаты.

| Код | Название |
| --- | --- |
| `CS-101` | Основы программирования |
| `CS-204` | Базы данных |
| `CS-305` | Разработка веб-приложений |
| `CS-410` | Машинное обучение |
| `CS-502` | Информационные системы |

### 4.2. Предложения

Таблица `suggestions` хранит:

- внутренний идентификатор предложения;
- время создания;
- исходное сообщение;
- шесть извлеченных полей;
- необязательную ссылку `course_id`;
- результат сопоставления `match_status`.

Исходный текст сохраняется отдельно от краткого содержания, сформированного моделью.

| Статус | Значение |
| --- | --- |
| `matched` | Курс с указанным кодом найден |
| `not_found` | Код указан, но курс отсутствует в справочнике |
| `not_provided` | Код курса не извлечен из сообщения |

Перед поиском код очищается от внешних пробелов и переводится в верхний регистр. Такие же правила применяются при заполнении справочника. Поиск выполняется по точному совпадению с `courses.code`.

Если курс не найден, извлеченный код сохраняется, а `course_id` остается равным `null`. Новые курсы по ответу модели не создаются.

## 5. Интеграция с языковой моделью

Подключение к LM Studio выполняется по адресу `http://127.0.0.1:1234/v1` через метод `client.chat.completions.create`.

Системная инструкция и пользовательское сообщение передаются раздельно. Инструкция описывает поля, допустимые категории и правила обработки отсутствующих сведений. Полный справочник курсов модели не передается.

Модель извлекает код из сообщения. Проверку существования курса выполняет приложение. Если указано только название курса без кода, поле `course_code` должно оставаться равным `null`.

Используются следующие параметры:

| Параметр | Значение |
| --- | --- |
| `temperature` | `0` |
| `max_tokens` | `512` |
| Тайм-аут по умолчанию | 60 секунд |
| `max_retries` | `0` |
| Формат ответа | `json_schema` |

Схема ответа формируется из модели Pydantic.

| Поле | Допустимое значение |
| --- | --- |
| `category` | `content`, `practice`, `schedule` или `other` |
| `summary` | Непустая строка |
| `course_code` | Строка или `null` |
| `topic` | Строка или `null` |
| `requested_change` | Строка или `null` |
| `details` | Строка или `null` |

Поле `details` содержит существенные сведения исходного сообщения, которые не вошли в остальные поля. Если таких сведений нет, возвращается `null`.

Отсутствующие данные не должны дополняться предположениями модели. Числа, даты и периоды сохраняются текстом. Для неоднозначной категории используется `other`.

При проверке ответа контролируются:

- наличие всех шести ключей;
- отсутствие дополнительных полей;
- соответствие типов;
- допустимость категории;
- непустое содержание `summary`.

Поля, допускающие `null`, объявлены без значений по умолчанию. Поэтому пропуск ключа считается ошибкой, а явно переданное значение `null` допускается. Пустые строки в этих полях преобразуются в `null`. Списки и объекты не преобразуются в строки.

После получения ответа проверяются наличие содержимого и завершенность генерации. Затем выполняются разбор JSON и проверка схемы. При ошибке результат не сохраняется.

Соответствие схеме не гарантирует точность извлечения, поэтому ответы дополнительно сравнивались с исходными сообщениями.

## 6. Реализация API

### 6.1. Маршруты

| Метод и маршрут | Назначение | Успешный ответ |
| --- | --- | --- |
| `POST /suggestions` | Создание предложения | `201 Created` |
| `GET /suggestions` | Получение списка предложений | `200 OK` |
| `GET /suggestions/{suggestion_id}` | Получение предложения по идентификатору | `200 OK` |

При отсутствии записи с указанным идентификатором возвращается `404 Not Found`.

Пример запроса:

```json
{
  "message": "хотелось бы перенести занятия на вечернее время"
}
```

До обращения к модели проверяется поле `message`. Отсутствующее поле, неверный тип, пустая строка и строка из пробелов отклоняются без вызова модели и сохранения записи.

Обработка корректного запроса включает следующие действия:

1. Вызов локальной модели.
2. Разбор и проверку ответа.
3. Нормализацию извлеченного кода.
4. Поиск курса в справочнике.
5. Определение статуса сопоставления.
6. Сохранение предложения и формирование ответа.

При ошибке базы данных выполняется откат транзакции.

### 6.2. Структура ответа

Пример фактического ответа на создание предложения:

```json
{
  "id": 28,
  "created_at": "2026-11-08T09:08:28.077752",
  "original_message": "хотелось бы перенести занятия на вечернее время",
  "category": "schedule",
  "summary": "Пользователь хочет изменить время проведения занятий.",
  "course_code": null,
  "topic": null,
  "requested_change": "перенести занятия на вечернее время",
  "details": null,
  "course_id": null,
  "course_name": null,
  "match_status": "not_provided"
}
```

Идентификатор, время создания, связь с курсом и статус сопоставления формируются приложением. Модель возвращает только шесть полей извлечения.

При чтении сохраненных записей повторный запрос к модели не выполняется.

## 8. Обработка ошибок и автоматические проверки

Ошибки возвращаются в едином формате с кодом и понятным описанием:

```json
{
  "error": {
    "code": "invalid_model_response",
    "message": "модель вернула некорректный ответ"
  }
}
```

В ответ не включаются секретные параметры и внутренние трассировки исключений.

| HTTP-код | Код ошибки | Причина |
| --- | --- | --- |
| `422` | `validation_error` | Неверное входное сообщение |
| `404` | `not_found` | Запись не найдена |
| `502` | `invalid_model_response` | Невалидный JSON или нарушение схемы ответа модели |
| `503` | `model_unavailable` | Сервер модели недоступен |
| `504` | `model_timeout` | Превышено время ожидания ответа |
| `500` | `internal_error` | Внутренняя ошибка приложения |

Для автоматической проверки создан файл `test_validation.py`. Используются отдельная база SQLite в памяти и подмена вызова клиента модели. Разбор JSON, проверка схемы, обработка запроса и сохранение выполняются кодом приложения.

| Проверка | Полученный результат |
| --- | --- |
| Пропуск каждого из шести обязательных ключей | `502`, запись не сохраняется |
| Невалидный JSON | `502`, запись не сохраняется |
| Дополнительное поле | `502`, запись не сохраняется |
| Пустой `summary` | `502`, запись не сохраняется |
| Список вместо строки | `502`, запись не сохраняется |
| Неизвестная категория | `502`, запись не сохраняется |
| Отсутствующее, числовое, пустое сообщение или строка из пробелов | `422`, модель не вызывается |
| Ошибка соединения с моделью | `503`, запись не сохраняется |
| Превышение времени ожидания | `504`, запись не сохраняется |
| Запрос отсутствующей записи | `404` |
| Корректный ответ со всеми ключами и допустимыми `null` | `201`, запись сохраняется |

Дополнительно проверяются структура объекта ошибки и отсутствие новых строк в базе после ошибочных запросов.

## 9. Возникшие трудности и внесенные исправления

При подключении к локальной модели возникла ошибка, связанная с настройками прокси. После отключения прокси подключение было проверено повторно.

Сервер не поддерживал первоначально указанный формат `json_object`. Для получения структурированного ответа использован формат `json_schema`.

По результатам запросов уточнена системная инструкция: описаны различия категорий, назначение полей и правила обработки отсутствующих сведений.

В схеме Pydantic все шесть ключей сделаны обязательными. Для полей, допускающих отсутствие информации, разрешено значение `null`, но пропуск ключа считается ошибкой. Дополнительные поля и значения неверного типа отклоняются.

Поиск курса выполняется по проверенному полю `course_code`. Обработка ошибок приведена к единому формату. После внесения исправлений выполнены автоматические проверки валидации, сетевых ошибок и сохранения данных.

## 10. Вывод

В ходе работы разработан API для обработки предложений по учебным курсам. Реализованы извлечение данных локальной языковой моделью, проверка структуры ответа, поиск курса по коду и сохранение результата в базе данных.

Проверена работа трех маршрутов API и всех статусов сопоставления: `matched`, `not_found`, `not_provided`. Неизвестный код не приводит к изменению справочника, а отсутствие сведений допускается с использованием `null`.

Автоматические проверки подтвердили обработку некорректных сообщений, ошибочных ответов модели, недоступности сервера и превышения времени ожидания. При проверенных ошибках записи не сохраняются.

При ручной проверке выявлены отдельные неточности модели: повтор сведений в `details`, недостаточно подробное описание действия и использование английского языка в части ответа. Эти результаты показали, что проверку схемы необходимо дополнять сравнением извлеченных данных с исходным сообщением.
